# Бенчмарки docid

[README](../README.md) → Бенчмарки

Бенчмарки измеряют операции `docid`: обработку документов, вычисление выражений, обслуживание индексов и выполнение запросов. Прямых замеров `json.Marshal`, Pebble или `btree` нет. Зависимости участвуют в работе модулей, поэтому их стоимость входит в результат соответствующей операции.

| Группа | Что измеряется |
| --- | --- |
| `BenchmarkDocument` | Кодирование и проверка документа из структуры, карты и `RawMessage`; чтение с сохранением `json.Number`; поиск обычных, вложенных и отсутствующих полей |
| `BenchmarkScalarComparison` | Нормализация и точное сравнение чисел, включая значения за пределами точности `float64` и большие показатели степени |
| `BenchmarkExprEval` | Вычисление готовых выражений DSL на 100 документах: диапазоны, вложенные поля, AND/OR/NOT/IN, отсутствующие поля и равенство полей JOIN |
| `BenchmarkIndexBuild`, `BenchmarkIndexMatches`, `BenchmarkIndexReplace` | Построение индексов по нормализованным документам, получение и упорядочивание ID кандидатов для всех поддерживаемых границ, замена значений с проверкой уникальности |
| `BenchmarkIndexCreateDrop` | Полный цикл создания уникального индекса по сохранённым документам и его удаления через API коллекции |
| `BenchmarkQueryFilter` | Одинаковые запросы с индексами и без них: выборки 1%, 10%, 50%, отсутствие совпадений, остаточный фильтр AND и перебор для OR |
| `BenchmarkQueryOrderPage` | Чтение всей коллекции, сортировка, пагинация и их сочетание |
| `BenchmarkQueryJoin` | INNER/LEFT JOIN, составное ON, WHERE после JOIN, цепочка JOIN; каждый сценарий с индексом и без него |
| `BenchmarkQueryDecode`, `BenchmarkQueryDecodeScan` | Полный путь `All`, `SelectInto` и `AllInto` для одинакового запроса: с фильтром и без него |
| `BenchmarkCollection` | `Get`, `GetInto`, параллельное чтение, замена через `Put`, цикл `Insert` + `Delete`; без индексов и с тремя индексами, включая уникальный |
| `BenchmarkDBLoad` | Загрузка метаданных и восстановление индексов функцией, которую вызывает `Open`, без запуска самого Pebble |
| `BenchmarkCollectionDurable` | Замена через публичный API с настоящей файловой системой и `pebble.Sync` |

Основная серия использует настоящий Pebble с файловой системой в памяти, сохраняя обычный путь чтения и записи. Это убирает ожидание дискового `Sync`, чтобы выделить затраты модулей проекта. Это **не** оценка производительности базы на диске: для неё выделена группа `BenchmarkCollectionDurable`, использующая `Open` и временный каталог. Она зависит от диска, файловой системы и нагрузки на машину.

Генерация данных, открытие хранилища, начальное заполнение, подготовка выражений и закрытие исключены из замеров. Серия проверяет повторное выполнение подготовленных запросов; стоимость построения DSL в неё не входит. Кроме `ParallelGet`, используется `testing.B.Loop` из Go 1.24. Все группы сообщают `ns/op`, `B/op`, `allocs/op` и проверяют результат. `docs/op`, `ids/op` и `rows/op` обозначают число обработанных документов, найденных кандидатов и возвращённых строк соответственно. В `ExprEval` одна операция обрабатывает 100 документов; в `IndexBuild` — всю коллекцию. В `InsertDelete` и `IndexCreateDrop` одна операция включает **оба** вызова API, а не один.

Данные детерминированы и не зависят от числа итераций: основные выборки содержат 100 и 1000 документов; коллекционные операции работают на 128 документах. Замена чередует два значения индексируемых полей, цикл вставки/удаления возвращает коллекцию в исходное состояние. JOIN использует 32 и 128 пользователей: у трёх четвертей по два заказа, у остальных нет заказов; у половины заказов есть платёж. Размеры JOIN ограничены, чтобы вложенный перебор оставался практичным. При `DBLoad` без индексов документы не читаются — это текущее поведение загрузчика.

Изменяющие коллекцию сценарии получают отдельное хранилище при каждом запуске, включая повторения `-count`, чтобы не наследовать историю записей других замеров. Число живых документов ограничено, однако версии записей, tombstone и фоновая работа Pebble внутри одного запуска остаются частью стоимости API. Для оценки собственно алгоритмов индекса и фильтров используйте отдельные группы `IndexBuild`/`IndexMatches`/`IndexReplace` и `ExprEval`.

Основная серия без дисковой группы:

```sh
go test -run '^$' -bench '^Benchmark(Document|ScalarComparison|ExprEval|Index.*|Query.*|Collection|DBLoad)$' -benchmem ./...
```

Быстрая проверка работоспособности всех сценариев; один проход не подходит для выводов о скорости:

```sh
go test -run '^$' -bench . -benchtime=1x ./...
```

Для анализа изменений запускайте выбранную группу несколько раз в одинаковых условиях, сохраняя результаты до и после изменения:

```sh
go test -run '^$' -bench '^BenchmarkQueryFilter$' -benchmem -benchtime=1s -count=10 ./... > before.txt
# После изменения:
go test -run '^$' -bench '^BenchmarkQueryFilter$' -benchmem -benchtime=1s -count=10 ./... > after.txt
```

Сравнивайте распределение результатов, учитывая разброс между запусками; не запускайте замеры одновременно с другими проверками. Для `ParallelGet` фиксируйте число процессоров, например `-cpu=1,4`. Отдельный замер записи на диск:

```sh
go test -run '^$' -bench '^BenchmarkCollectionDurable$' -benchmem -count=5 ./...
```
